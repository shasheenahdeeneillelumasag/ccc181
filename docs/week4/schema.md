## 2c. Choose types and constraints on purpose


| Table | Column | PostgreSQL type | Constraint | Why |
| --- | --- | --- | --- | --- |
| barangays | id | integer, generated | PRIMARY KEY | Generated by the database, never reused |
| barangays | name | varchar(60) | NOT NULL, UNIQUE | Every barangay has one name, and no barangay appears twice |
| barangays | slot_time | time | NOT NULL | The time of day when its families come, stored as a time, not text |
| barangays | active | boolean | NOT NULL, DEFAULT true | Flags whether the barangay is currently active or switched off |
| families | id | integer, generated | PRIMARY KEY | Generated by the database |
| families | head_name | varchar(100) | NOT NULL, CHECK (length(trim(head_name)) > 0) | A family must have a name, and a name of only spaces is rejected |
| families | household_size | integer | NOT NULL, CHECK (household_size >= 1 AND household_size <= 100 ) | A family has at least one member. |
| families | barangay_id | integer | NOT NULL, FOREIGN KEY REFERENCES barangays(id) ON DELETE RESTRICT | No family for a barangay that does not exist, and a barangay with families cannot be deleted |
| families | (barangay_id, head_name) | | UNIQUE | The same family is saved only once in one barangay. Without this, a family could get two rows and join the queue twice |
| tickets | id | integer, generated | PRIMARY KEY | This is the ticket number. Two families can never get the same number |
| tickets | family_id | integer | NOT NULL, FOREIGN KEY REFERENCES families(id) ON DELETE RESTRICT | No ticket for a family that does not exist, and a family with tickets cannot be deleted |
| tickets | status | varchar(20) | NOT NULL, DEFAULT 'waiting', CHECK (status IN ('waiting', 'called', 'received', 'no-show', 'left')) | Only these five values are allowed |
| tickets | created_at | timestamptz | NOT NULL, DEFAULT now() | Time zone safe, and set by the database when the family joins |
| tickets | called_at | timestamptz | NULL allowed, CHECK (called_at IS NULL OR called_at >= created_at) | Empty until staff call the family, and it can never be before the ticket was created |
| tickets | UNIQUE (family_id) WHERE status IN ('waiting', 'called') | | partial UNIQUE index | A family can have only one open ticket at a time |
| tickets | UNIQUE (family_id) WHERE status = 'received' | | partial UNIQUE index | A family can receive goods only once in this database, so a second received ticket is rejected |

**Note:**

- **Same family** means the same full name of the head of the family in the same barangay. Flask fixes the capitalization before saving. If two different families still match, maybe staff add a short note to one name.
- **Barangays are fixed.** They are added when the database is created.
- **One distribution.** A family receives goods once.
- **Join check.** Before joining, Flask checks that the family has not received goods and has no waiting or called ticket.
- **Joining again.** A family with a no-show or left ticket reuses its saved families row and gets a new ticket.

## 2d. Draw the ERD

![ERD](erd.png)

1. One barangay has many families. Each family belongs to exactly one barangay. (1:N)
2. One family has many tickets over time. Each ticket belongs to exactly one family. (1:N)

**What happens when a parent row is deleted?**
1. families.barangay_id > barangays.id is RESTRICTED because a barangay that has families cannot be deleted, so no family is lost by accident.
2. tickets.family_id > families.id is RESTRICTED because the tickets are the history of who received goods, so a family with tickets cannot be deleted.

## 2e. Check that it is normalized

1. **One value per cell (1NF):** No. No column holds a list. Each ticket has one status and one time.
2. **Depends on the whole key (2NF):** Not applicable, because there is no join table.
3. **No hidden copies (3NF):** No. A barangay's name and time slot are stored once, in barangays. A family's name and size are stored once, in families. A ticket does not repeat the barangay, because it can be found through the family. So I never have to update the same fact in more than one row.
